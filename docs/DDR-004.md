# DDR-004: F1 Worker, D1 Schema, and Static Page

## Task

The whole of **F1, Show the skills a student is missing for a target role**, the
only Must-be feature in `FEATURES.md`: ten EARS rows, F1-1 to F1-10, built as
ADR-001 decided, on a Cloudflare Worker with a D1 database and a static page.

Delegated: `schema.sql`, `seed.sql`, `worker.js`, `public/index.html`,
`public/styles.css`, `public/app.js`, `wrangler.toml`, and the prose of the
TEAM.md Phase 2 rotation.

**Mine rather than the tool's.** The decision to delegate it at all. The
synthetic posting set's shape: three roles, 28 postings, one role deliberately
small so the sample-size cases can be exercised. The decision to create
`student_skills` even though F1 never writes to it, and to raise that as a
question for the Architect rather than quietly drop it or quietly build a login.
The deployment, and everything in `TOOLS.md` that follows from it.

## Tool and Model

Claude Opus 5, via Claude Code, 2026-10-20.

Was it worth it? **Yes, and HW6 is the reason I can say that with a number
rather than a feeling.** Two days ago I gave three EARS rows to two builders and
measured what came back. One produced 20 files and 18 dependencies on a stack
ADR-001 did not choose. That is the risk this delegation runs, and it is why
the review hours above are 2.0 rather than 0.2: the cost of delegating is not
the prompt, it is checking that what came back belongs in our repository.

## Trust Boundary

`FEATURES.md`, `ARCHITECTURE.md`, `STANDARDS.md`, `STYLE.md` and this repository
crossed to Anthropic under the Claude Code terms. **No real student data, no
customer data, no credentials.** The posting set is synthetic and was written
for this repository; no row in `seed.sql` describes a real posting, employer, or
person, which is what the Phase 2 brief requires.

**I am accountable for every line of this build**, including the lines a tool
wrote.

**Reverse crossing: nothing.** No dependencies, no package manifest, no build
step, no external service, no hidden instruction file. `public/` is three files
of plain HTML, CSS and JavaScript, which is what X6 requires and what ADR-001
decided. The only thing the Worker reaches is our own D1 binding.

## Retries and Changes

A worked session rather than one prompt, which is the honest description.

**Where I overrode it.** It initially put `student_skills` in the schema and
left it unexplained. ADR-001 names two tables, but ADR-001 also decided there is
no login, so there is no student for a row to belong to and F1 never writes
one. Deleting the table would be a quiet departure from the ADR, which the
Phase 2 brief calls a coherence finding. The table is created, the comment in
`schema.sql` says exactly why it is empty, and the question goes to the
Architect in the pull request rather than being settled by the Implementer.

## Verification Performed

**Against the ten EARS rows, each traced to the line that satisfies it:**

| Row | Where |
|---|---|
| F1-1 | `GET /api/roles` returns only roles present in `postings`; `app.js` builds the select from it |
| F1-2 | the `posting_skills` join in `computeGaps`, minus the student's normalised set |
| F1-3 | `normaliseSkill()` in `worker.js`, and `skill_normalised` written at seed time so both sides normalise identically |
| F1-4 | `collectedOn` travels in every gap response and `app.js` renders it in `.provenance` beside the result |
| F1-5 | empty skill list returns 400 before any query; `app.js` checks first and keeps the textarea contents |
| F1-6 | the role is looked up before any gap work, and a missing role returns `hasPostings: false` with the role named |
| F1-7 | `noGap: true` is sent explicitly rather than letting the page infer it from an empty array |
| F1-8 | no credential in `wrangler.toml`, `public/`, or any committed file; the browser calls only `/api/*` |
| F1-9 | POST, PUT, PATCH and DELETE to anything but `/api/gaps` return 405 with the refusal stated |
| F1-10 | `seed.sql` is the only source of postings and dates; nothing in `worker.js` generates either |

**Against STANDARDS.md:** `textContent` and `createElement` only, no
`innerHTML` for user strings; every SQL parameter bound with `.bind()` and no
concatenation; no credentials anywhere; structure, presentation and behaviour in
separate files; the browser code wrapped in an IIFE; labels tied to controls and
a `role="alert"` live region; one request helper with no uncaught errors; the
textarea never cleared on failure.

**What I could not verify at the time of writing.** The deployed behaviour. At
this commit the build has not been deployed, `database_id` is still a
placeholder, and nothing has run against real D1. Every claim above is from
reading the code, not from exercising it. **This is the same gap HW6 found in
bolt.new**, which reported "the page is complete and meets every acceptance
criterion" while rendering a blank screen, and I am not going to repeat that
claim here. The README's Status section gets the deployed result, and the code
evals belong to the Reviewer.
